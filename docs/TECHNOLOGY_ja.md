# harness-threadbox で使っている技術の解説（入門者向け）

このドキュメントは、`hthreadbox` がどんな技術とライブラリで作られているかを、
ソフトウェア開発を始めたばかりの人にも分かるように説明したものです。
途中で出てくる専門用語は、その場か文末の「用語集」で説明しています。

原文（英語）は [TECHNOLOGY.md](TECHNOLOGY.md) です。内容が食い違う場合は英語版を正とします。

---

## 1. 全体像：このツールは何をしているのか

Claude Code は、あなたとの会話を 1 行 1 レコードのテキストファイル
（JSONL 形式、後述）としてホームディレクトリの `~/.claude/projects/` に書き残します。
`hthreadbox` はそのファイルを読み、端末（ターミナル）の画面に
「Claude Code を使っていたときと同じ見え方」で描き直します。
やっていることを順番に並べると次の 4 段階です。

```
① ファイルを見つける  →  ② 1 行ずつ読んで意味を解釈する
       →  ③ 画面に出す形（文字列と色）に組み立てる  →  ④ 端末に描く・キー入力に反応する
```

ソースコードのフォルダもこの 4 段階に対応しています。

| フォルダ | 役割 | 段階 |
|---|---|---|
| `src/providers/claude/` | Claude Code のログを探し、読み、共通の形に変換する | ①② |
| `src/core/` | ツール全体で共有するデータの形（型）と、セッション一覧の管理 | ② |
| `src/render/` | 文字列と色の組み立て。Markdown の変換や折り返しもここ | ③ |
| `src/tui/` | 端末の制御、画面の描画、キーボードとマウスの処理 | ④ |
| `src/cli/` | コマンドライン引数の解釈と `cat` / `list` / `export` サブコマンド | ①〜③ の組み合わせ |

## 2. 言語と実行環境

### TypeScript

JavaScript に「型」を付け足した言語です。型とは「この変数には数値しか入らない」
「この関数は文字列を返す」といった約束のことで、コンパイラ（後述）が
約束違反をプログラム実行前に見つけてくれます。
このプロジェクトではもっとも厳しい設定（`strict` など）を有効にしていて、
たとえば「配列の 5 番目の要素は存在しないかもしれない」ことまで型で表現させています
（`noUncheckedIndexedAccess`）。入門者には少し厳しく感じますが、
実行してから「undefined は読めません」というエラーに出会う回数が激減します。

- **コンパイル**：人間が書いた TypeScript を、Node.js が実行できる JavaScript に変換する作業。
  `npm run build` が `tsc`（TypeScript コンパイラ）を呼び、`src/` から `dist/` へ変換します。
- **tsx**：コンパイルせずに TypeScript ファイルを直接実行できる開発用ツール。
  `npm run dev -- list` のように使い、動作確認を素早く回せます。

### Node.js 24

JavaScript をブラウザの外（サーバやコマンドライン）で動かすための実行環境です。
ファイルを読む、端末を操作する、ファイルの変更を監視する、といった
OS の機能を JavaScript から使えます。このプロジェクトは Node.js 24 以上を要求し、
ブラウザの JavaScript には無い次の標準モジュールを使っています。

| モジュール | 用途 |
|---|---|
| `node:fs` | ファイルの読み書き、`stat`（サイズや更新時刻の取得）、`fs.watch`（変更の監視） |
| `node:path` | パス（ファイルの場所を表す文字列）の結合や相対化。Windows の `\` も正しく扱う |
| `node:os` | ホームディレクトリの取得など |
| `node:tty` | 端末の「生モード」切替（後述） |
| `process` | 標準入出力、環境変数、終了コード、シグナル（Ctrl-C など）の処理 |

### ESM（ECMAScript Modules）

ファイル同士を `import` / `export` でつなぐ、現在標準のモジュール方式です。
`package.json` の `"type": "module"` がその宣言です。古い方式（CommonJS、`require()`）
との違いとして、import 先に拡張子 `.js` を明示する必要があります。
TypeScript のソースでも `import ... from './foo.js'` と書くのはこのためです
（コンパイル後に `.js` になるファイルを指しているため）。

### npm

Node.js のパッケージ管理ツールです。`package.json` に「このプロジェクトが使う
ライブラリ」と「よく使うコマンドの短縮名（scripts）」を書き、
`npm install` で取得、`npm run build` などで実行します。
`package-lock.json` は取得したライブラリの正確な版を記録したファイルで、
別のマシンでも同じ版が入るようにするためのものです。

## 3. 使っているライブラリ（実行時に必要なもの）

実行時の依存はわざと 3 つに絞っています。ライブラリが少ないほど、
インストールが速く、将来壊れる箇所も減るからです。

### markdown-it

Claude の返答は Markdown（`**太字**` や `- 箇条書き` などの軽量な記法）で
書かれています。markdown-it はその文章を「トークン」の列に分解してくれます。
トークンとは「ここから見出し」「ここは強調」「ここはコードブロック」といった
意味付きの部品のことです。

普通はトークンから HTML を作りますが、このツールは端末に出すので、
トークンを受け取って **ANSI エスケープシーケンス**（後述）で色や太字を付ける
独自の変換器を `src/render/markdown.ts` に書きました。
既製の「Markdown を端末向けに変換するライブラリ」を使わなかった理由は、
折り返し（長い行を画面幅で改行すること）を文字数ではなく **表示幅** で
正確に行う必要があったからです（次項）。

### string-width と get-east-asian-width

端末では、日本語や中国語の文字（CJK）は英数字の 2 倍の幅で表示されます。
絵文字も 2 幅、結合文字（濁点だけの文字など）は 0 幅です。
「この文字列は画面上で何マス使うか」を数えるのが `string-width`、
1 文字ずつの幅（1 か 2 か）を判定するのが `get-east-asian-width` です。

これが重要なのは、画面に出す行の長さが 1 マスでもずれると、
端末が勝手に折り返して表示全体が崩れるからです。
また、このツールは「セッション全体で何行になるか」を計算してスクロール位置を
決めているので、折り返しの結果は毎回同じ（決定的）でなければなりません。

文字の区切りには Node.js 標準の `Intl.Segmenter` も併用しています。
これは「人間が 1 文字と感じる単位（グラフェム）」で文字列を切る機能で、
たとえば肌の色を指定した絵文字のように複数のコード単位からなる 1 文字を
途中で分断しないために使います。

## 4. 開発時だけ使うツール

| ツール | 役割 | 一言で |
|---|---|---|
| **TypeScript (`tsc`)** | コンパイルと型チェック | 「約束違反」を実行前に見つける |
| **tsx** | TypeScript を直接実行 | ビルド無しで試す |
| **vitest** | テスト実行 | 「期待どおり動くか」を自動で確かめる |
| **eslint** + **typescript-eslint** | 静的解析（リンター） | 書き方のミスや危ない書き方を指摘する |
| **@types/node**, **@types/markdown-it** | 型定義 | JavaScript 製ライブラリに型情報を与える |

### テスト（vitest）

テストとは「この入力ならこの出力になるはず」をプログラムとして書いておき、
変更のたびに自動で確かめる仕組みです。`npm test` で 48 件のテストが走ります。
このプロジェクトでは次の 3 種類を書いています。

1. **ユニットテスト**：1 つの関数を単独で試す。例：折り返し関数に CJK 混じりの
   文字列を渡し、「どの行も指定幅を超えない」ことを確かめる（`test/wrap.test.ts`）。
2. **フィクスチャ（見本データ）を使ったテスト**：Claude Code の実際のログと同じ形の
   JSONL を `test/helpers.ts` の関数で生成し、解釈結果（ターン数やツールの対応付け）を
   確かめる。実データは個人情報を含むので、形だけを真似た見本を使います。
3. **エンドツーエンド（E2E）テスト**：偽の端末（`FakeTerminal`）と偽のログ供給元
   （`FakeProvider`）を用意し、本物と同じ `App` を動かしてキーを送り、
   画面のスナップショット（文字列の配列）を検査する（`test/app.test.ts`）。
   端末が無くても TUI 全体を試せるのが利点です。

### リンター（eslint）

コンパイルは通るが怪しい書き方（使っていない変数、`==` と `===` の混同など）
を指摘するツールです。チームで書き方を揃える目的にも使います。

### スモークテスト

「煙が出ないか確かめる」程度の、ざっくりした動作確認です。
`scripts/smoke.mjs` は実際の `~/.claude` に対して `list` / `cat` / `export` を実行し、
エラー無く終わるか、巨大なセッションを数秒以内に描けるかを見ます。
`scripts/tui-smoke.sh` は **tmux**（端末を仮想的に作れるツール）の中で TUI を起動し、
キーを送って画面を取得し、終了後に端末が元に戻るかを確認します。

## 5. 端末（ターミナル）をどう制御しているか

ここがこのツールの中で一番「低レベル」な部分です。
一般的な TUI ライブラリ（Ink、blessed など）を使わず自作しました。
理由は、10 万行規模の仮想的な文書を 1 行単位で差分描画したかったことと、
候補ライブラリが古い（保守されていない）か、新しすぎる Node.js を要求したためです。
自作部分は `src/tui/` の約 700 行で、使っている仕組みは次のとおりです。

### ANSI エスケープシーケンス

端末に「ここから赤色」「カーソルを 3 行目へ」などを指示する特別な文字列です。
すべて `ESC`（文字コード 27、JavaScript では `\x1b`）で始まります。例：

| 文字列 | 意味 |
|---|---|
| `\x1b[31m` | 以降の文字を赤にする（SGR = Select Graphic Rendition） |
| `\x1b[0m` | 色や太字を解除 |
| `\x1b[5;1H` | カーソルを 5 行目 1 桁目へ |
| `\x1b[?1049h` / `l` | 代替スクリーンへ切替 / 戻す（終了時に元の画面が復活するのはこのため） |
| `\x1b[?25l` / `h` | カーソルを隠す / 表示 |
| `\x1b[?1000;1002;1006h` | マウスのクリック・ドラッグ・ホイールを報告させる（SGR マウスモード） |
| `\x1b[?2026h` / `l` | 同期出力：この間の描画を端末がまとめて反映し、ちらつきを防ぐ |

### 生モード（raw mode）

通常、端末は Enter が押されるまで入力を溜め、Ctrl-C でプログラムを強制終了します。
`process.stdin.setRawMode(true)` でこれを止めると、1 キーごとに即座に入力が届き、
Ctrl-C も単なる文字として受け取れます。代わりに、終了時に必ず元へ戻す責任が
生じるので、`src/tui/terminal.ts` は正常終了・エラー・シグナルのどの経路でも
復元処理が走るようにしています。

### 入力の解釈（`src/tui/input.ts`）

キーボードの矢印キーや PageUp は 1 バイトではなく `\x1b[A` のような
エスケープシーケンスで届きます。マウスも `\x1b[<0;10;5M`（ボタン 0 を
10 桁 5 行目で押した）という形です。これらを 1 バイトずつ読み、
「キー名」や「マウスイベント」というプログラムが扱いやすい形に変換します。
ESC キー単独とエスケープシーケンスの先頭を区別するため、30 ミリ秒待って
続きが来なければ ESC 単独と判断しています。

### 差分描画（`src/tui/screen.ts`）

毎回画面全体を書き直すと遅く、ちらつきます。そこで「前回表示した各行」を
覚えておき、変わった行だけをカーソル移動して書き換えます。
これを **ダブルバッファ** と呼びます（2 枚の画面内容を持って比べる、という意味）。

## 6. Claude Code のログの読み方

### JSONL

**JSON** は `{"name": "値", "count": 3}` のようにデータを書く標準的な書式です。
**JSONL**（JSON Lines）は、1 行につき 1 つの JSON を並べたファイルで、
末尾に追記しやすく、途中の 1 行が壊れても他の行は読めるという利点があります。
Claude Code はこの形式で、ユーザーの発言、Claude の返答、ツールの実行結果などを
1 件ずつ追記しています。

### 追記を安全に読む（`src/providers/claude/jsonlTailer.ts`）

ライブ表示では、Claude Code が書き込み中のファイルを横から読みます。
難しいのは「ファイルの最後の行がまだ書き終わっていない」場合があることです。
このツールは「前回どこまで読んだか（オフセット＝ファイル先頭からのバイト数）」を
覚え、新しく増えた部分のうち **最後の改行まで** だけを処理し、
途中までしか無い行は次回に回します。
改行の位置はバイト列のまま探します。UTF-8（日本語などを 1〜4 バイトで表す方式）
の文字がまたがる位置で切ると文字化けするためです。

### 正規化（`src/providers/claude/normalizer.ts`）

Claude Code のログには、画面に出すべきものと出さないもの、
分割されて複数行に分かれた 1 つの返答などが混ざっています。
これを「ターン（1 回の発言）」と「ブロック（文章・思考・ツール呼び出し）」という
ツール独自の分かりやすい形に組み替える処理を **正規化** と呼んでいます。
将来 Codex や Gemini のログに対応するときは、この正規化だけを書けば
画面側のコードはそのまま使えます（後述の Provider 抽象）。

### ファイル変更の監視

`fs.watch` は OS から「このフォルダの中身が変わった」という通知を受け取る機能です。
通知の内容は OS によってあてにならないので、通知が来たら必ず `stat` で
ファイルサイズを測り直して判断します。また、通知を取り逃す場合に備え、
実行中と分かっているファイルは 2 秒ごとに念のため確認（ポーリング）しています。
短時間に大量の通知が来ても処理が暴走しないよう、200 ミリ秒まとめて 1 回に
する **デバウンス** も行っています。

### 実行中セッションの検出

Claude Code は実行中に `~/.claude/sessions/<プロセス ID>.json` を書きます。
そのプロセス ID に対して「シグナル 0 を送る」（`process.kill(pid, 0)`。
実際には何も送らず、存在確認だけを行う慣用句）ことで、
まだ生きているかを判定しています。

## 7. 画面の組み立て方の工夫

### 仮想ドキュメントとセッション固定のカーソル（`src/tui/document.ts`）

右ペインは、選んだプロジェクトの全セッションを縦につなげた 1 本の長い文書として
扱います。ただし全部を一度にメモリに読むと重いので、見える場所の周辺だけを
読み込み、読んでいないセッションは「見出し + 読み込み中…」の 3 行で代用します。

ここで問題になるのが「上のセッションが読み込まれて 3 行から 500 行に増えたら、
今見ている場所がずれる」ことです。そのため現在位置を「全体の何行目」ではなく
「どのセッションの何行目」として覚えています。上で何が起きても、
見ている場所は動きません。

### 行キャッシュと累積和（`src/render/lineCache.ts`）

セッションの描画結果（行の配列）はターンごとに保存し、変更があったターンだけ
作り直します。「N 行目はどのターンか」を素早く求めるため、各ターンの行数を
先頭から足し上げた表（累積和）を持ち、二分探索で探します。
これで 14 MB のセッションでも 0.5 秒程度で描けます。

### LRU キャッシュ

読み込んだセッションは最大 6〜8 個までメモリに置き、それを超えたら
「最も長く使われていないもの（Least Recently Used）」から捨てます。
ただし今画面に見えているものは捨てないよう保護しています。

### Provider 抽象

「ログを探す・読む・正規化する」部分を `Provider` という共通の窓口（インターフェース）
にまとめ、画面側はその窓口しか知らないようにしています。
インターフェースとは「この名前のメソッドがあり、こういう値を返す」という
約束だけを定めたもので、実装は差し替えられます。Claude Code 用が
`src/providers/claude/` にあり、Codex 用などを足すときは同じ約束を満たす
フォルダを追加して登録するだけです。

## 8. 用語集

| 用語 | 意味 |
|---|---|
| **TUI** | Text User Interface。文字だけで作る対話的な画面。マウスも使えるが、描画は文字のマス目 |
| **CLI** | Command Line Interface。コマンドと引数を打って実行し、結果を文字で受け取る方式 |
| **ターミナル／端末** | 文字の入出力を行う画面。Windows Terminal、GNOME Terminal、tmux の中の画面など |
| **シェル** | 端末でコマンドを受け付けるプログラム。bash、zsh、PowerShell など |
| **コンパイル** | 人が書いたコードを、機械や実行環境が扱える形に変換すること |
| **型** | 変数や関数が扱う値の種類の約束。違反を実行前に検出できる |
| **モジュール** | 1 つのファイル単位の部品。`import` で他のモジュールの機能を使う |
| **インターフェース** | メソッド名と型だけを定めた約束。実装を差し替え可能にする |
| **JSON / JSONL** | データの書式。JSONL は 1 行 1 JSON を並べたもの |
| **UTF-8** | 世界中の文字を 1〜4 バイトで表す符号化方式。日本語は多くが 3 バイト |
| **バイト／オフセット** | バイトはデータの最小単位（8 ビット）。オフセットは先頭から何バイト目か |
| **グラフェム** | 人間が 1 文字と認識する単位。複数のコードから成る絵文字なども 1 グラフェム |
| **表示幅** | 端末上で占めるマス数。英数字 1、日本語 2、結合文字 0 |
| **ANSI エスケープシーケンス** | `ESC [` で始まる端末制御命令。色、カーソル移動、モード切替 |
| **生モード（raw mode）** | 端末が入力を加工せず、1 キーずつ即時に渡すモード |
| **代替スクリーン** | 全画面アプリ用の別画面。終了すると元のシェル画面が戻る |
| **ダブルバッファ／差分描画** | 前回の画面を覚えておき、変わった部分だけ描き直す技法 |
| **デバウンス** | 短時間に連続する出来事をまとめ、最後の 1 回だけ処理する技法 |
| **ポーリング** | 一定間隔で状態を見に行くこと。通知を取り逃したときの保険 |
| **キャッシュ** | 計算や読み込みの結果を取っておき、再利用して速くする仕組み |
| **LRU** | Least Recently Used。キャッシュが満杯のとき、一番使われていないものを捨てる方針 |
| **累積和** | 先頭からの合計を並べた表。区間の合計や「何番目か」を速く求められる |
| **二分探索** | 並んだデータを半分ずつ絞って探す方法。10 万件でも 17 回程度で見つかる |
| **正規化** | ばらつきのある入力データを、扱いやすい統一された形に整えること |
| **プロセス ID（pid）** | OS が実行中プログラムに付ける番号 |
| **シグナル** | OS がプロセスに送る合図。Ctrl-C は SIGINT。シグナル 0 は存在確認用 |
| **リンター** | コードの書き方の問題を指摘する静的解析ツール |
| **ユニットテスト／E2E テスト** | 部品単体の試験／利用者と同じ操作で全体を通す試験 |
| **フィクスチャ** | テスト用に用意する見本データ |
| **スモークテスト** | 大きな壊れが無いかだけを素早く見る粗い試験 |
| **シンボリックリンク／ジャンクション** | 別の場所にあるファイルやフォルダを指す「近道」。`npm link` が使う |
| **tmux** | 1 つの端末の中に複数の仮想端末を作るツール。自動テストで TUI を動かすのにも使う |
